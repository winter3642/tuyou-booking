# 压测报告（W4D3）

> 工具：JMeter 5.6.3（非 GUI 模式，计划文件 `scripts/bench/*.jmx`，可 GUI 打开复现/截图）
> 环境：本机 Windows + Docker Compose 三容器（应用 / MySQL 8（1G 缓冲池）/ Redis 7）
> 数据量：产品 10 万 / SKU 50 万 / 用户 51 万 / 订单 100 万+ / 明细 200 万
> 日期：2026-09-10

## 一、超卖验证（核心结果）

**场景**：SKU 库存置 100 → 清空 Redis 库存缓存 → **1000 并发**各下单 1 件（每用户预置购物车，JMeter CSV 参数化 token/cartId）。

**结果**：

| 指标 | 期望 | 实测 |
|---|---|---|
| 成功下单数 | 100 | **100**（DB 按订单时间窗精确计数） |
| 成交件数 | 100 | **100**（明细 100 条，每单 1 件） |
| 被拒绝请求 | 900 | **900**（全部返回"库存不足"） |
| DB 库存终值 | 0 | **0**（无负库存） |
| Redis 库存终值 | 0 | **0** |
| 超卖 | 0 | **0** ✅ |

1000 个并发请求里恰好 100 个成功——Redis Lua 原子扣减 + DB 条件扣减（`UPDATE ... WHERE stock>=?`）双保险，超卖率 0。

## 二、下单接口压测（200 并发 × 50 轮）

**计划**：200 线程 / Ramp-up 20s / 每线程循环 50 次，每轮真实闭环「加购 → 查购物车 → 下单」，共 30000 请求（JMeter `scripts/bench/qps.jmx`）。

| 轮次 | 配置 | 吞吐 | avg | 业务成功率 | 结论 |
|---|---|---|---|---|---|
| 1 | 容器应用，Hikari 10 / Tomcat 200（默认） | 157 req/s | 1139ms | 99.5%（CSV token 复用互踩） | 基线 |
| 2 | Hikari 50 / Tomcat 300 | 157 req/s | 1154ms | 同上 | **吞吐不变 → 排除连接池瓶颈** |
| 3 | 每循环唯一用户（10000 用户 CSV） | 122 req/s | 1499ms | **100%**（10000 单全部落库） | 修正数据问题 |
| 4 | MySQL 缓冲池 128MB→1G | 155 req/s | 1155ms | — | **不变 → 排除缓冲池** |
| 5 | 原生 JVM（同库同 Redis） | 122 req/s | 1499ms | **100%** | 与应用形态无关 |

**瓶颈结论**：所有轮次都卡在 ~120-160 req/s，而压测期间应用/MySQL/Redis 容器 CPU 均 <1%。瓶颈是 **Docker Desktop（Windows）的端口转发 userland 代理**（本机形态专属；Linux 服务器上不存在此限制）。排除过程：连接池 10→100、Tomcat 线程 200→1500、MySQL 缓冲池 128MB→1G、容器换原生 JVM——吞吐均不变化，锁定端口转发层。

> 简历口径建议：写"下单接口本机 40+ 单/s、超卖率 0"如实可复现；如上线 Linux 服务器后复测，吞吐数字会显著不同（端口转发限制消失）。

## 三、调优迭代记录（面试素材）

| 迭代 | 动作 | 结果 |
|---|---|---|
| ① 连接池 | Hikari 10→50→100，Tomcat 200→300→1500 | 无变化 → 应用不是瓶颈 |
| ② 数据修正 | JMeter CSV 200 行被 200 线程×50 轮复用 → 同用户并发互踩购物车，~0.5% 业务失败；改为 10000 个唯一用户后成功率 100% | 压测数据准备坑 |
| ③ 数据库 | MySQL 容器缓冲池 128MB→1G（1M 订单表超过默认内存） | 吞吐不变（被端口转发盖住），但保留调优 |
| ④ 形态对比 | 容器应用 vs 原生 JVM（同一 MySQL/Redis） | 吞吐相近 → 端口转发为天花板 |

## 四、踩坑记录

1. **HTTP 200 不等于业务成功**：业务失败（库存不足）也返回 HTTP 200 + `code:400`，JMeter 的 `success` 字段全 true——最终校验必须查 DB（按订单时间窗精确计数），不能只看 JMeter 报告。
2. **订单 create_time 是 DB 默认值（UTC）**：按时间窗统计要先换算时区（容器 MySQL 为 UTC）。
3. **Redis 库存必须先清**：超卖验证前 `DEL stock:sku:{id}`，否则测的是上次压测的残留库存，结果全错。
4. **下单接口吃 cartIds**：压测每轮必须「加购 → 查车提取 id → 下单」，且下单成功会清空购物车，循环设计要配套。
5. **Windows Docker Desktop 端口转发 ~155 req/s 天花板**：压测"部署形态吞吐"与"应用能力"要分开测。

## 五、复现方法

```bash
# 1. 起环境（compose 三容器 + 造数）
docker compose up -d
TUYOU_DB_PORT=3307 python scripts/gen_data.py
# 2. 准备用户（超卖场景带 --cart）
python scripts/bench/gen_users.py --count 1000 --url http://localhost:8082 --sku 1 --cart --out scripts/bench/users_oversell.csv
# 3. 生成计划并执行（需 JMeter 5.6.3，解压后）
python scripts/bench/gen_jmx.py --base-url http://localhost:8082
jmeter -n -t scripts/bench/qps.jmx -l scripts/bench/results_qps.jtl
jmeter -n -t scripts/bench/oversell.jmx -l scripts/bench/results_oversell.jtl
# 4. 分析
python scripts/bench/analyze.py scripts/bench/results_qps.jtl
# 5. 超卖口径以 DB 为准：
#    SELECT COUNT(*) FROM t_order WHERE order_no LIKE 'TO%' AND create_time BETWEEN ...;
#    SELECT stock FROM t_product_sku WHERE id=1;  → 0
```
