# 面试讲稿：途游预订项目技术点追问预案（W4D5）

> 用法：每个技术点给 3 个追问预案 + 1 句"主动引导话术"。回答原则：**先结论 → 再机制 → 最后落到本项目真实数据**。所有数字出自本项目实测（README/压测报告）。

---

## 1. Redis + Lua 防超卖（主打点）

**主述（30 秒）**：库存扣减用 Redis Lua 脚本原子完成"读库存→判断→扣减"，DB 用条件更新 `UPDATE ... SET stock=stock-? WHERE stock>=?` 兜底，双写最终一致；1000 并发抢 100 库存实测成功下单恰好 100、库存终值 0、无负库存。

**追问预案**：

1. **"Lua 为什么能保证原子性？"** → Redis 单线程串行执行命令，Lua 脚本整体作为"一条命令"提交，执行期间不可能被其他客户端的命令插入——所以"先 GET 再 DECR"的两步竞态（两个请求都读到 100 再都扣成 99）在脚本里不存在。
2. **"Redis 扣了 DB 没扣成怎么办？"** → 下单事务里 DB 条件扣减失败（比如行锁冲突、库存被改）会抛异常：事务回滚 DB 侧，catch 里用 INCRBY 把 Redis 预扣还回去；如果进程崩溃还不了，Redis 库存会短暂偏小——所以我选了"宁少不超卖"的偏小方向，代价是可能误拒单，通过定时对账脚本 DB 库存回写 Redis 兜底。
3. **"Lua 返回 -1（未初始化）怎么处理？"** → 该 SKU 第一次被访问：从 DB 读真实库存 SETNX 回写 Redis（幂等，不覆盖已扣减中的值），再重试一次脚本；SETNX 保证并发下只有第一个请求真正写入。

**引导话术**：我会主动提"为什么不是减库存成功才写订单，而是先 Redis 后 DB 的双保险"，把话题引到自己做过的并发测试上。

## 2. 慢 SQL 优化：FULLTEXT 与索引设计

**主述**：搜索接口从 `LIKE '%kw%'` 全索引扫描改为 ngram 全文索引，低频词 SQL 耗时 88.7ms→37.8ms、API ~180ms→~100ms；EXPLAIN 从 `type=ref/rows=49631` 变成 `type=fulltext/rows=1`。

**追问预案**：

1. **"前导通配符为什么走不了索引？"** → B+Tree 按列值字典序组织，`LIKE '%桂林%'` 无法确定前缀区间，只能全扫描；`LIKE '桂林%'` 能走 range 是因为前缀确定了区间起点。我还做了函数包裹列、隐式类型转换两个失效实验对照。
2. **"ngram 全文索引的取舍？"** → 实测发现全文检索有固定解析成本（~40-55ms/条），高频词场景 LIKE 靠 LIMIT 提前截断反而打平；它真正的价值是把**最坏情况**（命中率低时扫 5 万行）压掉、性能不随命中率波动。另外 ngram 最小切词 2 字符，单字关键词搜不到——生产会配合 ES 或 edge-ngram。这段取舍我记录在 README 优化专题。
3. **"等值在前、范围在后是为什么？"** → B+Tree 联合索引按列序排列，等值列先定位、范围列在索引内连续扫描、排序列跟上消除 filesort；把范围列放前面会导致后面等值列无法利用索引序，全退化。

**引导话术**：主动讲"我记录了 EXPLAIN 和 API 双口径数据，发现两者不一致"——展示自己会验证而不是背结论。

## 3. 深分页延迟关联

**主述**：`LIMIT 90000,20` 每跳一行都要回表取整行再丢弃，改成两步：① 覆盖索引只取主键（Extra=Using index，零回表）② 主键 IN 取回 20 行并重排。EXPLAIN ANALYZE CPU 成本 91.5ms→21.6ms。

**追问预案**：

1. **"为什么延迟关联快？"** → 把"跳过 9 万行的代价"从"索引遍历+每行回表取整行"降为"纯索引遍历"（每行只读 8 字节主键），回表只发生在最终 20 行上；本质是把 O(offset×行宽) 变成 O(offset×主键宽 + pageSize×行宽)。
2. **"为什么不用游标分页？"** → 游标（`WHERE id > 上页最后id`）更快但无法跳页、无法拿到 total；产品列表业务要求跳页和总页数，所以选延迟关联。如果做 Feed 流这种无限下拉场景我就用游标——**方案跟着业务形态选**。
3. **"API 实测差异不明显，为什么还要做？"**（诚实点）→ 10 万行且缓冲池全热时回表发生在内存，两方案 API 级都 ~20ms；EXPLAIN ANALYZE 的差距是 CPU 成本。数据量到百万级或缓存冷时回表变磁盘 IO，差距才会放大——**优化要先分清 CPU 成本与 IO 成本，并如实记录，不拿假数字写简历**。

## 4. 缓存三防（穿透/击穿/雪崩）

**主述**：穿透用空值缓存 60s；击穿用 Redisson 互斥锁 + 双重检查，抢不到锁的等 50ms 重读缓存、读不到就降级查库；雪崩用 TTL 600s + 0~300s 随机抖动。

**追问预案**：

1. **"击穿为什么不选逻辑过期？"** → 逻辑过期（value 带 expireAt，过期后旧值继续用、异步重建）不阻塞用户但要接受短暂旧数据；详情页数据一致性要求高（价格/库存），互斥锁方案牺牲一点等待换强一致。**场景不同取舍不同**。
2. **"互斥锁重建时抢不到锁的请求怎么办？"** → 等 50ms 重读缓存（大概率已回填），还是读不到就降级直查库——保证可用性优先；加锁失败还可能抛 InterruptedException，规范做法是恢复中断标记后降级。
3. **"为什么 TTL 要加随机抖动？"** → 大量 key 同批过期后集体回源，DB 瞬时被打爆就是雪崩；随机抖动把回源时间打散。配合预热接口（启动/定时把热数据提前灌进缓存）双保险。

## 5. JWT 鉴权与 ThreadLocal

**主述**：登录签发 HS384 JWT（7 天），拦截器校验后把 userId/username 放 ThreadLocal，请求结束 afterCompletion 里 clear。

**追问预案**：

1. **"ThreadLocal 不清理会怎样？"** → Tomcat 线程池复用线程，下一个请求会读到上一个用户的 userId——串号；同时线程池常驻导致 ThreadLocal 引用的对象无法回收，内存泄漏。所以必须在 finally/afterCompletion 清理。
2. **"JWT 怎么登出/踢人？"** → 无状态 JWT 本身无法失效，靠服务端手段：token 白名单/黑名单存 Redis（本项目预留了方案，实现的是简化版）。也可以缩短有效期 + refresh token 组合。
3. **"越权怎么防的？"** → 订单详情/购物车修改这类按 id 操作的接口，Service 层查出来先校验 `order.userId == 当前登录用户` 否则 403——**归属校验必须放在 Service 层而不是只靠前端隐藏按钮**，测试里专门写了"admin 访问 test01 的订单返回 403"的用例。

## 6. 工程化：测试 / CI / 部署

**主述**：104 个测试全绿、JaCoCo 95.9%；GitHub Actions 里起 MySQL+Redis 服务容器跑全量测试，绿了才构建镜像推 GHCR；Docker Compose 编排三容器一键部署。

**追问预案**：

1. **"CI 里跑测试的坑？"** → 测试要连 MySQL/Redis，GitHub Actions 用 services 起容器，健康检查就绪才开始跑；本地测试账号 tuyou 在 CI 不存在，通过环境变量覆盖连接配置（本地默认值零配置）；Redis 密码漏配会全红，排障思路是"先在本地 mvn test 确认，再看 CI 与本地差异：时区/密码/初始化"。
2. **"覆盖率怎么算的，95.9% 是不是水分？"** → JaCoCo 行覆盖，entity/dto/vo 纯数据类排除；覆盖率高不等于测试好，我的用例重点在分支：库存不足、回滚、越权、锁分支——MockMvc 走的是真数据库+真 Redis 的全链路，不是全 mock。
3. **"多阶段构建好在哪？"** → builder 阶段打包、运行时只带 JRE 镜像，最终镜像不带 Maven/源码，体积小攻击面小；pom 先 COPY 再 go-offline，源码不变时依赖层命中缓存，构建快。

## 一句话版本（电梯演讲 60 秒）

> 途游预订是一个旅游产品预订系统，10 张表、10 万产品 100 万订单的数据量。技术上我重点做了三件事：一是订单链路用 Redis Lua 原子扣减 + DB 条件更新双保险防超卖，1000 并发抢 100 库存实测零超卖；二是慢 SQL 优化，关键词搜索用 ngram 全文索引替代 LIKE 全扫描、深分页用延迟关联消除九万次回表，优化前后数据都实测记录在 README；三是工程化，104 个测试 95.9% 覆盖率、GitHub Actions 带 MySQL/Redis 服务容器跑测试并推送镜像、Docker Compose 一键部署。所有数字可复现，压测报告和 EXPLAIN 记录都在仓库里。
